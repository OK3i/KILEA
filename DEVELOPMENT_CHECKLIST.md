# ModForge — план разработки

Чеклист объединяет этапы из раздела 9 ТЗ в пять последовательных фаз.
Отмечайте пункт `[x]` после реализации и проверки критерия завершения.

## Phase 1 — Требования и проектирование

**Результат:** согласованные требования и схема данных, по которым можно начинать разработку.

- [x] Зафиксировать цель, пользователей, роли и функциональные требования в ТЗ.
- [x] Определить PostgreSQL-модель: `users`, `games`, `categories`, `projects`,
  `project_versions`, `reviews`, `favorites`.
- [x] Реализовать TypeORM-сущности, связи, enum ролей и уникальные ограничения
  для отзывов и избранного.
- [ ] Сохранить исходник ER-диаграммы (например, DBML для dbdiagram.io) в репозитории.
- [ ] Сверить ER-диаграмму, сущности и раздел 12 ТЗ: имена полей, типы, nullable,
  значения по умолчанию и внешние ключи.

**Критерий завершения:** требования однозначны; диаграмма и сущности отражают
одну и ту же модель данных.

## Phase 2 — Каркас приложения и доступ

**Результат:** запускаемый NestJS API с модульной структурой, проверкой входных данных
и работающей аутентификацией.

- [x] Настроить NestJS, глобальный префикс `/api`, Swagger и `ValidationPipe`.
- [x] Разделить backend на модули `Auth`, `Users`, `Projects`, `Reviews`, `Database`.
- [x] Реализовать регистрацию, хеширование пароля и выдачу JWT при входе.
- [ ] Добавить тесты регистрации и входа: успешный сценарий, неверный пароль,
  повторный email и некорректный ввод.
- [ ] Реализовать получение и обновление собственного профиля; не возвращать
  `passwordHash` в API.
- [x] Реализовать авторизацию по ролям `user`, `author`, `admin`; проверять
  права на backend для каждого защищённого действия.
- [x] Добавить server-side ownership guard для проектов и их версий:
  автор может управлять только своими ресурсами, администратор — любыми.
- [ ] Добавить тесты доступа: пользователь не может менять чужие данные;
  автор управляет только собственными проектами; администратор имеет
  предусмотренные ТЗ полномочия.

**Критерий завершения:** API запускается, входные DTO валидируются, аутентификация
и проверки полномочий подтверждены тестами.

## Phase 3 — Каталог и основные сценарии API

**Результат:** посетитель может находить и просматривать проекты, а автор —
создавать и сопровождать собственные проекты и версии.

- [x] Реализовать DTO, Swagger и API проектов: список, фильтры, поиск, пагинация,
  просмотр проекта, создание, обновление, удаление и добавление версий.
- [ ] Реализовать API чтения игр и категорий, необходимые для каталога и фильтров.
- [ ] Проверить, что публичный каталог и карточка проекта показывают только
  опубликованные проекты; автор и администратор могут видеть проекты
  согласно своим правам.
- [ ] Завершить CRUD игр и категорий для администратора.
- [ ] Добавить интеграционные тесты проекта: поиск и фильтры по игре, категории
  и автору; просмотр версий; проверка прав владельца; удаление зависимых данных.
- [ ] Описать API-контракты и типовые ошибки в Swagger.

**Критерий завершения:** ключевые сценарии поиска, просмотра и управления проектами
работают через API и покрыты тестами.

## Phase 4 — PostgreSQL, миграции и контейнеры

**Результат:** приложение воспроизводимо запускается с PostgreSQL; структура БД
обновляется контролируемо, а не только автоматически.

- [x] Подключить TypeORM к PostgreSQL через `DATABASE_URL`.
- [x] Добавить PostgreSQL-драйвер, Dockerfile backend и Compose-сервисы
  PostgreSQL, backend и frontend.
- [x] Настроить healthcheck PostgreSQL и ожидание готовности базы для backend.
- [x] Проверить сборку контейнеров и запуск всего Compose-стека.
- [ ] Создать начальную TypeORM-миграцию для всех таблиц, связей, enum и индексов.
- [ ] Отключить `synchronize` в обычном и production-запуске; создавать и менять
  схему только миграциями.
- [ ] Проверить применение миграций на пустой БД и сохранность данных при
  повторном запуске с Docker volume.
- [ ] Хранить секреты и пароли вне образов и репозитория; задать сильные значения
  через окружение при развёртывании.

**Критерий завершения:** чистый запуск `docker compose up --build` поднимает
PostgreSQL, backend и frontend; миграции создают схему, healthcheck-и проходят.
